# Multi-Service Hostname + NodePort Connectivity Remediation Plan

## 1) Root-cause analysis per service

### Global (affects all services except cases masked by fallback)
1. **Named host does not inherently map to NodePort**
   - DNS resolution (`<service>.<domain>`) and NodePort transport (`<node-ip>:<nodePort>`) are separate layers.
   - Current system returns named external host but does not yet provide a deterministic local DNS/port-binding layer for every protocol.
2. **App-to-service traffic blocked by secure egress policy (already patched recently)**
   - Internal cluster connectivity from app pods to managed service pods can fail unless explicit egress rules allow DB/cache/queue ports.
3. **Connection metadata is generated by service-specific logic spread across worker and credential utility**
   - This increases drift risk between host, port, protocol, and URI formatting.

### PostgreSQL (ETIMEDOUT)
Likely contributors:
- App used external endpoint path with unresolved host/port mapping instead of internal ClusterIP DNS.
- Or pod egress policy blocked internal traffic on 5432 before policy fix.
- URI scheme compatibility (`postgresql://` vs `postgres://`) may vary by some client libraries.

### MongoDB / Redis / RabbitMQ / MinIO / OpenSearch
Likely contributors:
- Same hostname-to-NodePort gap as PostgreSQL when using external host from inside cluster.
- Protocol-specific expectations not fully normalized in one shared output object:
  - Redis auth URI handling
  - RabbitMQ dual-port behavior (AMQP vs management UI)
  - HTTP services (MinIO/OpenSearch) vs raw TCP services.

### MySQL (working reference)
- Has correct port exposure and usable connection metadata in current path.
- Must remain unchanged functionally; only generalize same reliability pattern to all other services.

---

## 2) Differences between MySQL and failing services

1. **Operational confidence gap, not intended code-path gap**
   - MySQL has been validated end-to-end in your environment.
   - Other services rely on same NodePort generation pattern but are not validated with protocol-specific client expectations.
2. **Protocol-specific behavior differs by service**
   - MySQL/Postgres/Mongo/Redis/RabbitMQ AMQP are TCP clients.
   - MinIO/OpenSearch require HTTP semantics and health checks.
3. **Secondary ports and alternate URIs are not first-class in one standardized response contract**
   - RabbitMQ and MinIO especially need explicit protocol-aware endpoint fields.

---

## 3) Fix strategy

### Phase A — Centralize and normalize output
Create a single utility:

`generateServiceConnection(serviceInstance, catalog, runtime)`

Return:
- `internal_host`
- `external_host`
- `fallback_host`
- `port`
- `protocol`
- `connection_uri`
- `fallback_uri`
- `secondary_endpoints[]` (e.g., rabbitmq-management, minio-console)

### Phase B — Keep transport stable
- Keep NodePort for external exposure exactly as transport baseline.
- Keep ClusterIP DNS for in-cluster traffic.
- Do not change MySQL working transport behavior.

### Phase C — Protocol-aware endpoint generation
- Generate URI per service with explicit scheme and auth style.
- Emit primary + secondary endpoint metadata from one table-driven map.

### Phase D — Local hostname reliability
- Support preferred named host in API (`<service>.localhost`) and fallback host.
- Add local DNS setup automation options:
  - wildcard localhost if resolver supports it,
  - otherwise hosts-file helper command output,
  - optional wildcard dev domain.

---

## 4) Updated host/port logic (standard)

For every managed service instance:

- `service_name = <serviceType>-<projectId>`
- `namespace = project-<projectId>`
- `internal_host = <service_name>.<namespace>.svc.cluster.local`
- `external_host`:
  - local: `<service_name>.localhost`
  - production: `<service_name>.<SERVICE_EXTERNAL_BASE_DOMAIN | PROJECT_DOMAIN>`
- `fallback_host` (local): `localhost`
- `port`: service primary protocol port

NodePort mapping remains source of truth for external port, attached to `external_port` and `fallback_port`.

---

## 5) Connection string fixes (protocol-aware)

Use a shared map:
- postgresql: `postgres://user:pass@host:port/db` (+ optional alias `postgresql://` for compatibility)
- mysql: `mysql://user:pass@host:port/db`
- mongodb: `mongodb://user:pass@host:port/db?authSource=admin`
- redis: `redis://:pass@host:port`
- rabbitmq: `amqp://user:pass@host:port/vhost`
- minio: `http://host:port`
- opensearch/elasticsearch: `http://user:pass@host:port`

Also emit explicit `client_examples` per service (CLI/library snippets) to reduce misconfiguration.

---

## 6) Code changes required

1. **New shared utility**
   - Add `Utils/serviceConnectionResolver.js` (wrapper over host resolver + URI map + endpoint metadata).
2. **Provision worker refactor**
   - Replace ad-hoc connection assembly with shared resolver output.
   - Persist normalized object in `connectionDetails`.
3. **Credential manager alignment**
   - Move URI scheme map into shared resolver or export a reusable map to avoid duplicated logic.
4. **Service details API response contract**
   - Return normalized fields:
     - `internal_host`, `external_host`, `fallback_host`, `port`, `connection_uri`, `fallback_uri`, `secondary_endpoints`.
5. **Local DNS helper endpoint**
   - Add endpoint that returns hosts-file instructions for unresolved named hosts (OS-specific).
6. **Validation hooks**
   - Add post-provision TCP/HTTP probe per service type against both internal and external endpoints (when enabled).

---

## 7) Edge cases

1. **ETIMEDOUT vs ECONNREFUSED diagnostics**
   - ETIMEDOUT: routing/DNS/firewall/policy issue.
   - ECONNREFUSED: service reachable but not listening/ready.
2. **Windows DNS behavior for `*.localhost`**
   - Not always consistent across CLI tools; fallback or helper mapping required.
3. **NodePort allocation drift**
   - Re-read assigned NodePort after service creation; never assume static port.
4. **Secondary port confusion (RabbitMQ/MinIO)**
   - Must expose explicit endpoint names and protocols.
5. **Cross-namespace policy regression**
   - Ensure secure egress policy keeps allowing managed service ports.
6. **Legacy instances**
   - Preserve legacy connectionDetails fields while adding normalized fields to avoid frontend breakage.
