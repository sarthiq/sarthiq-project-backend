# Sarthiq Platform Networking & Service Exposure Implementation Plan

## 1) Current system analysis

### 1.1 Service provisioning lifecycle
- Service instances are created via `createService` and queued for asynchronous provisioning.
- Current service instance naming is `${serviceType}-${projectId}-${random}`.
- Current namespace convention for managed services is `sarthiq-svc-${projectId}`.
- The worker (`serviceProvisionWorker`) creates Kubernetes resources in this order: Secret, ConfigMap, PVC, StatefulSet/Deployment, ClusterIP Service, and currently always an external NodePort Service.
- Connection metadata currently persists an internal DNS host and an external host derived from `svc.<domain>` plus NodePort.

### 1.2 Kubernetes resources currently used
- Managed services are generated by `kubeServiceBuilder`.
- Internal service exposure is ClusterIP.
- External exposure currently uses NodePort via `buildNodePortService`.
- Resource naming convention inside Kubernetes is `svc-${serviceType}-${instanceId}`.
- Labels already encode ownership and traceability (`managed-by`, `sarthiq.com/service-type`, `sarthiq.com/projectId`, `sarthiq.com/instanceId`).

### 1.3 Deployment/subdomain ingress (app deployments)
- App deployments (project frontend/backend) already use HTTP Ingress routing from `${subdomain}.${baseDomain}` through NGINX ingress.
- This ingress path is separate from managed infrastructure service exposure and must remain untouched.

### 1.4 Gaps against target requirements
- External access is not optional today; NodePort is always created.
- Naming/namespace do not match required patterns (`<serviceType>-<projectId>`, `project-<projectId>`).
- No centralized host generation function for deterministic internal/external endpoints.
- No TCP ingress mapping for production domains per service instance.
- No explicit external exposure security gate (auth/IP whitelist) in service exposure orchestration.

## 2) Target naming conventions and identity model

### 2.1 Canonical naming rules (new)
- **Namespace:** `project-<projectId>`
- **Primary Service name (ClusterIP):** `<serviceType>-<projectId>`
- **Optional external exposure resource names:**
  - Local NodePort service: `<serviceType>-<projectId>-external`
  - Production TCP ingress backend reference uses the primary ClusterIP service

### 2.2 Backward compatibility and migration-safe aliasing
Because the current platform already uses `svc-${serviceType}-${instanceId}` and `sarthiq-svc-${projectId}`, introduce a compatibility phase:
1. Keep existing resource naming for already-provisioned instances.
2. For newly provisioned instances, adopt canonical naming.
3. Add deterministic labels/annotations on all new resources:
   - `sarthiq.com/canonical-service-name=<serviceType>-<projectId>`
   - `sarthiq.com/canonical-namespace=project-<projectId>`
4. During transition, allow host resolution utility to fallback to legacy names if canonical resource not found.

## 3) Centralized host generation logic

Create `Utils/serviceHostResolver.js` with:

```js
generateServiceHost(serviceInstance, environment)
// returns { internal_host, external_host, port }
```

### 3.1 Inputs
- `serviceInstance`: includes `ProjectId`, `instanceName`, `ServiceCatalog.defaultPort`, `externalAccessEnabled`, `namespace`, and resolved `serviceType`.
- `environment`: derived from config (`local` | `production`) instead of raw `NODE_ENV` only.

### 3.2 Resolution logic
1. Resolve canonical `serviceName = <serviceType>-<projectId>`.
2. Resolve canonical namespace `project-<projectId>`.
3. Build internal DNS: `<serviceName>.<namespace>.svc.cluster.local`.
4. If `externalAccessEnabled !== true`, return `external_host = null`.
5. If enabled:
   - production: `<serviceName>.sarthiq.in`
   - local: `<serviceName>.localhost`
6. Return port from service catalog (`defaultPort`) unless explicit override exists for mapped secondary ports.

### 3.3 Usage points (mandatory injection points)
- `Jobs/serviceProvisionWorker.js`: replace ad-hoc `internalHost` / `externalHost` assembly.
- `Controller/User/serviceController.js`: service detail/list API should return resolved hosts from centralized function.
- `Utils/credentialManager.js` call sites: pass generated host output into `buildConnectionDetails`.

## 4) Data model and API changes

### 4.1 ServiceInstances schema
Add fields to `ServiceInstance` model:
- `externalAccessEnabled` (BOOLEAN, default `false`)
- `externalAccessConfig` (JSON, nullable) for:
  - `mode`: `nodeport` | `tcp-ingress`
  - `ipWhitelist`: string[]
  - `authSecretRef` or generated credential metadata

### 4.2 Create/update API behavior
- `POST /api/services/create` accepts optional `externalAccessEnabled` and `externalAccessConfig`.
- Validation rules:
  - default false
  - if true, validate user plan/permissions and service compatibility
  - reject unsafe configs (invalid CIDR, forbidden open ranges when policy requires restrictions)

## 5) Kubernetes resource behavior changes

### 5.1 Internal communication (always on)
- Always create ClusterIP service with canonical name.
- Ensure selector targets exact app label of managed service workload.
- Keep StatefulSet/Deployment behavior unchanged per service catalog.

### 5.2 External access (conditional)
Only create additional exposure resources when `externalAccessEnabled=true`.

#### Local (Docker Desktop Kubernetes)
- Preferred mode: NodePort service (`<service>-<projectId>-external`), auto-assigned nodePort.
- Domain mapping strategy:
  - `*.localhost` hostnames resolve to `127.0.0.1` in modern resolvers.
  - For environments lacking wildcard localhost behavior, document `/etc/hosts` fallback for each endpoint.
- Routing:
  - `<service>-<projectId>.localhost:<nodePort>` → NodePort service → pod.

#### Production (`sarthiq.in`)
- Preferred mode: TCP ingress via ingress-nginx stream configuration (or Traefik `IngressRouteTCP`).
- Domain pattern: `<service>-<projectId>.sarthiq.in`.
- Implement controller-managed mapping object (e.g., ConfigMap for nginx stream) per exposed service.
- Keep service type ClusterIP; ingress handles L4 entry and forwards to `<service>-<projectId>.<namespace>:<port>`.

### 5.3 Dynamic port assignment and conflict avoidance
- Local NodePort: let Kubernetes auto-assign to avoid collisions.
- Production TCP ingress:
  - If using SNI-capable TCP router, no per-service external port conflicts on 443/3306 entrypoint.
  - If static port map is required, maintain centralized allocator table persisted in DB/ConfigMap.

## 6) Ingress / proxy design for non-HTTP services

### 6.1 NGINX ingress (TCP stream) option
- Use ingress-nginx `tcp-services` ConfigMap in `ingress-nginx` namespace.
- Operator/controller path in backend:
  1. On external enable, add mapping key `<publicPort>` -> `<namespace>/<serviceName>:<targetPort>`.
  2. Ensure ingress controller service exposes mapped TCP port.
  3. Create/update DNS record for `<service>-<projectId>.sarthiq.in` to ingress LB/entrypoint.

### 6.2 Traefik option
- Create `IngressRouteTCP` + `TLSStore`/SNI rules for each exposed service.
- Prefer wildcard cert `*.sarthiq.in` and SNI-based routing for protocol-agnostic TCP where client supports TLS SNI.

### 6.3 Recommendation for Sarthiq
- Short-term: keep local NodePort; production TCP ingress through ingress-nginx stream map.
- Mid-term: converge both envs on a single gateway abstraction if a unified ingress stack is standardized.

## 7) Security model

### 7.1 Default posture
- `externalAccessEnabled = false` by default.
- Internal DNS remains always available inside cluster only.

### 7.2 External authentication requirements
For externally exposed services, enforce one of:
1. Native service credentials generated by platform and rotated.
2. Gateway-level auth where protocol supports it (limited for raw TCP).

At minimum:
- Return credentials only to authorized user.
- Store encrypted connection details only.
- Rotate password on exposure toggle or on-demand.

### 7.3 IP allowlist
- Add optional CIDR allowlist in `externalAccessConfig.ipWhitelist`.
- Enforce through NetworkPolicy and/or gateway allowlist controls.
- Deny-all except allowlisted CIDRs when configured.

### 7.4 Additional hardening
- Audit log for external exposure create/update/delete.
- Rate-limit exposure toggles.
- Optional TTL-based auto-disable for temporary public endpoints.

## 8) Routing and traffic flow (end-to-end)

### 8.1 Internal
`Backend Pod` → `mysql-abc123.project-abc123.svc.cluster.local:3306` → `ClusterIP Service` → `MySQL Pod`

### 8.2 External (production)
`mysql-abc123.sarthiq.in` → `TCP Ingress (NGINX/Traefik)` → `ClusterIP Service mysql-abc123` → `Pod:3306`

### 8.3 External (local)
`mysql-abc123.localhost:<nodePort>` → `NodePort Service mysql-abc123-external` → `Pod:3306`

## 9) Validation plan

### 9.1 Internal connectivity checks
- From backend pod namespace, run DNS + TCP checks to managed service internal host.
- Validate injected env vars use `*.svc.cluster.local` host.

### 9.2 External connectivity checks
- Local:
  - Verify `<service>-<projectId>.localhost` resolves.
  - Verify TCP connect on assigned NodePort.
- Production:
  - Verify domain DNS record exists.
  - Verify ingress route forwards to target service/port.

### 9.3 Regression checks
- Service creation/deletion still works for existing instances.
- Existing app ingress for project deployments remains unaffected.
- Delete flow removes conditional external resources only when present.

## 10) Edge cases and failure handling

1. **NodePort exhaustion/conflicts:** rely on auto-assignment; if exhausted, surface actionable error.
2. **DNS propagation delays in production:** mark external endpoint as `pending_dns` until resolvable.
3. **Wildcard localhost unsupported on some systems:** provide explicit `/etc/hosts` fallback instructions.
4. **Service rename incompatibility:** avoid renaming live resources in-place; use compatibility resolver and phased migration.
5. **Ingress controller absent/misconfigured:** pre-flight check before enabling external access.
6. **Credential leak risk:** never log plaintext credentials; redact connection URIs in worker logs.
7. **Protocol mismatch through gateway:** keep protocol-specific checks (MySQL handshake, Redis PING) in health validation.

## 11) Phased implementation sequence

1. Add schema fields (`externalAccessEnabled`, `externalAccessConfig`) + migration.
2. Implement `generateServiceHost(serviceInstance, environment)` utility with canonical and legacy fallback support.
3. Refactor provision worker to:
   - always create ClusterIP
   - only create external resources when enabled
   - use centralized host resolver.
4. Refactor service APIs to expose resolved hosts consistently.
5. Add local external exposure module (NodePort lifecycle + returned endpoint metadata).
6. Add production TCP ingress mapping module.
7. Add security enforcement (auth, whitelist, audit).
8. Add integration tests and rollout behind feature flag (`SERVICE_EXTERNAL_EXPOSURE_V2`).
